# In The Picture CMS integration — staged, NOT connected

The CMS half is implemented here, but the website still needs the matching revision/tombstone changes and a verified media allowlist. **Do not set tokens, schedule a cron, run production migrations, or send posts until both sides pass a cross-app test.** Incoming briefs never publish articles. Existing CMS `blog-prompts` are a separate feature.

## Contract and ownership

- Scope by `IN_THE_PICTURE_CLIENT_ID` (positive numeric Payload client ID). CMS ideas have unique website UUID `blogId`. Only editors with the `blog-ideas` feature can see this client's ideas; website-owned brief, status and rank fields cannot be edited via Payload. Editors own `editorNotes` and `linkedPost` (same client only).
- Website → CMS: `POST /api/content-sync/ideas`, `Authorization: Bearer <CONTENT_CMS_IDEAS_TOKEN>`, <=500 KB; `{version:1,ideas:[...]}` max 100, exact UUIDs unique within a batch. Each idea supplies `blogId`, 1-based `priority`, `blogIdea`, `suggestedTitle`, `mainPoint`, `keyPoints`, `pointsToAvoid`, `supportingContent`, `contributor`, `idealAuthor`, `status` (`open`/`published`), `publishedSlug`, ISO `updatedAt`, positive integer `recordRevision`, `orderRevision`. Edits only advance record revision, rank/creation advances order revision; equal revision with conflicting values rejects the whole transaction. A stale record can still carry a newer rank. CMS never deletes an idea because it disappears from a feed.
- Repair pull: fixed `IN_THE_PICTURE_WEBSITE_ORIGIN` (HTTPS only, localhost HTTP in development), `GET /api/content-sync/ideas?offset=N&limit=100`, Bearer `CONTENT_CMS_SYNC_TOKEN`. Response `{version:1,ideas:[...],total,nextOffset,snapshotRevision,orderRevision}`. The CMS validates every page, restarts on changed snapshot, checks IDs/total/1-based ranks, then applies the complete snapshot in one transaction. At most 1,000 ideas per traversal; if the site needs more, agree a new bounded pagination strategy first.
- CMS → website: `POST /api/content-sync/articles` with the same **separate** `CONTENT_CMS_SYNC_TOKEN`, 2 MB max, exact post ID and monotonically increasing ISO `revision`, `published`/`unpublished`. Only client-confirmed, published posts for the fixed client are queued. Explicit `websiteBlogIdeaId` is validated against a stored idea; no title matching. Website `author` must exactly match a public author name on this client's CMS profile at `/api/public/blog-authors/{clientId}`. Category and service are chosen by editors, not inferred. Categories: `tax-tips`, `business-handbook`, `contractor-handbook`; services are the 12 exact slugs in the website `src/lib/site.ts` as of this handoff. `readTime` is CMS `readingTime`, `publishDate` is the YYYY-MM-DD from `publishedDate`. Only a restricted Markdown/Lexical subset is converted; other nodes fail rather than disappear. Public CMS-origin images require useful alt text; Vercel Blob URLs are blocked until the website's **exact** allowlisted origin is agreed and the converter updated.
- CMS sync-event records persist the exact client ID and snapshot the article JSON before network delivery; no hook fetches the website. Claims and manual retries also check the persisted client ID, so changing configuration cannot deliver an older client's events. Edits, unpublish and deletion queue revisions; a later publish supersedes older publish work, never unpublished tombstones. A cron leases at most eight events per tick, with 12-second timeouts and bounded backoff; 409/422 stay in visible `review` state. Acknowledgment is only recorded on the website's documented 200 response; manual retry needs an admin session, matching request origin and `blog-posts` feature. `POST /api/content-sync/tick` with `{}` runs manual pull/backfill/delivery or `{"eventKey":"postId:revision"}` retries one event. `GET /api/content-sync/tick` is cron-only with `CRON_SECRET`. No cron is registered yet; enable only after website rollout.

## Migration and deployment handoff (not performed)

- Check `src/migrations/20260926_120000_in_the_picture_sync.ts`, the shared SQL in `src/lib/in-the-picture/schema.ts`, and the idempotent production runner addition in `src/lib/run-migrations.ts`. New `blog_ideas`/`blog_sync_events` tables, post/version columns and Payload locked-document relations are additive. Do not schema-push in production. Back up real data, review older website migrations `0011`, `0012` and its new migration on a production-shaped copy, and test restore before any production migration.
- Verify client ID and public media URLs. CMS server env: `IN_THE_PICTURE_CLIENT_ID`, `IN_THE_PICTURE_WEBSITE_ORIGIN`, `CONTENT_CMS_IDEAS_TOKEN` (website→CMS), `CONTENT_CMS_SYNC_TOKEN` (CMS→website), `CONTENT_CMS_PUBLIC_ORIGIN` (canonical HTTPS CMS media origin), existing `CRON_SECRET`. Two independent randomly generated >=32-character secrets; configure separately on both deployments. Never put tokens in browser env or logs.
- First run a manual pull, review idea links/category/service/bylines/media, then manually run historical-post backfill/delivery against a test website. Only after successful cross-app outage/retry tests, enable a scheduled cron (e.g. `/api/content-sync/tick`). No automatic connection is enabled by this change.
